# 금융 공유 캐시 범위 보강 — 검토 전용

운영 DB, 설정, 권한 정책과 기존 장부 행은 변경하지 않았다. 아래는 최초 `finance`와 `finance_limits` 두 dataset 보강 당시의 기록이다. 최종 통합에서는 같은 보호를 `prestock`까지 확대했으며, 실패 원복·누락 원본 확인을 포함한 최신 결과는 `staged-prestock-ledger.md`, `staged-financial-source-completeness.md`와 `staged-audit-v2184.md`를 따른다.

## 확인한 문제와 수정

회사 단위 서버 revision이 남아 있다는 사실은 공용 localStorage 키의 현재 본문이 그 회사 소유임을 보장하지 않는다. 다른 회사가 열린 탭에서 키를 교체하면, 레거시 회사 식별자가 없는 채무를 잘못 합산하거나 다음 CAS에 다른 회사 본문을 보낼 수 있었다.

두 dataset의 실제 인증된 hydration 본문을 회사·user 객체·client 객체·hydration epoch에 결합한 메모리 snapshot으로 보관한다. 조회에는 복제본만 제공한다. 현재 역할과 readiness를 확인하기 전에는 읽기·수정에 사용하지 않는다. 기존 회사 장부에만 남은 퇴사자 채무도 이 확인된 본문에서 계속 조회한다.

CAS flush의 일반 읽기와 충돌 재확인 후 읽기, idle 복구 표식 생성 및 ACK 재확인도 같은 snapshot을 사용한다. 금융사 목록 복원 역시 공용 raw 키를 다시 읽지 않는다. 본래 revision/CAS/ACK/재시도 및 최신 정상 저장 후 표식 정리는 유지한다.

## 기존 복구 표식의 한계

기존 표식은 hash만 보관하므로 공용 raw 키 본문의 회사 소유권을 증명하지 못한다. 같은 회사·user·client·epoch에 결합된 이전 메모리 본문이 있으면 그 본문으로만 복구 판정한다. 그 본문이 없으면, 권한을 확인한 서버의 정확한 저장 완료 응답과 일치하는 경우만 ACK로 처리한다. 나머지는 충돌 상태와 기존 캐시·표식을 유지하며 자동 재전송하지 않는다. 다른 회사의 캐시를 현재 회사의 화면 본문으로 채택하지 않는다.

따라서 새 로그인에서 출처를 확인할 수 없는 구형 금융 복구 표식은 자동 재시도 대신 확인이 필요할 수 있다. 새로운 payload를 추정하거나 과거 장부를 자동 수정하지 않는다.

## 검증

- 실제 두 탭을 사용한 공용 키 교체: 1440/390px에서 조회·금융 CAS·설정 CAS가 현재 회사 본문을 유지하고 다른 탭 raw 캐시를 덮어쓰지 않음.
- user/client/company/역할/epoch 및 지연 hydration 응답의 차단.
- 기존 계약중→판매완료→부분상환→완납 및 재고 복귀 PC/모바일 회귀.
- 실제 inline helper를 사용하는 금융 복구 30건, 기존 복구 통합 17건, 복구 모듈 8건, 금융 계산 5건, 선재고 설정 범위 6건.
- 기존 가상 자동 로그아웃·실패/응답 유실 저장 복구 브라우저 회귀.
- 로그인 테스트의 너무 짧은 오답 비밀번호 fixture를 정상 길이의 가상 오답으로 변경하여 실제 Auth 거부·재시도 경로를 시험. 기존 HTML 확인 팝업도 실제 확인 버튼을 눌러 진행하도록 harness를 맞춤. 제품 인증 조건은 변경하지 않음.

그 밖의 shared dataset 캐시 사용은 이번 보강에 섞지 않고 별도 검토 대상으로 남긴다. 배포나 main 병합은 수행하지 않는다.

## 최초 게이트 당시 로그인 전체 회귀의 남은 검증

기준 main 6a569c5의 원본 테스트도 너무 짧은 오답 비밀번호로 native form-validation 팝업에 막히는 것을 재현했다. 정상 길이의 가상 오답으로 맞춘 뒤 앞의 동시 로그인 2건 및 Auth 거부·재시도·기억된 로그인 복원은 통과했다. 그 다음의 전체 로그인 회귀는 로그아웃 확인 팝업을 기다리는 기존 fixture 경로에서 완료하지 못했다. HTML 확인 버튼을 실제 클릭하는 bounded helper를 추가했으나 확인창이 나타나지 않아 타임아웃되었으며, 원인을 제품 문제로 단정하지 않는다. 금융 scope와 자동 로그아웃의 독립 회귀는 통과했고, 나머지 전체 로그인 검증은 2단계에서 계속한다.

후속 2단계에서 원래 로그아웃 확인창의 실제 버튼을 처리하도록 fixture를 고쳐 정상 로그인 전체 10그룹을 통과했다. 제품 인증·세션 조건은 완화하지 않았다. 완료 결과와 운영 미검증 범위는 `staged-login-review.md`에 보관한다.
