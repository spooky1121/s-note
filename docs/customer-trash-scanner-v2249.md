## 고객 삭제

계약서 자동저장이 끝나기 전에 고객 목록을 읽으면 목록의 수정 시각이 이미 오래된 값이 될 수 있다. 삭제는 저장 완료를 기다린 뒤에도 목록 버튼의 이전 수정 시각으로 요청해 서버의 엄격한 CAS 검사에서 거절된다. 기존 오류 처리는 목록 버전을 그대로 두므로 반복 클릭도 충돌한다. 최근 운영 로그는 고객 내용 없이 함수 단계·SQLSTATE만 집계했으며, 해당 삭제 경로의 오류는 수정 시각/복원 세대 비교 위치의 `40001`이었다.

또한 고객 삭제에 사용되지 않는 차량·금융·첨부의 전역 저장 준비를 기다리는 경로도 있었다. 고객 삭제는 고객의 저장 순서와 서버 확인을 지키며 다른 업무의 저장 충돌로 막히지 않도록 분리한다. 동시 수정 충돌을 무시하거나 최신 정보를 자동으로 삭제하지 않는다.

정상 삭제는 기존 서버 휴지통 확인 후 해당 고객만 목록에서 즉시 제거한다. 실제 충돌은 같은 목록에서 최신 정보를 다시 읽고 사용자에게 재확인을 안내한다. 검색·정렬·보기·페이지를 유지하며, 식별번호와 목록 요청에는 이전 응답이 새 자료를 덮지 못하도록 요청 세대를 적용한다. 삭제 확인과 목록 제거는 정확한 수정 시각 원문·복원 세대를 포함한 선택 토큰도 검사하므로 늦은 응답이 복원된 고객을 지우지 못한다. 고객별 저장 직렬화와 서버 CAS·상사/소유자/세션 권한은 유지한다.

## 스캐너

검증된 기존 migration `20261126165102_accountant_scanner_inbox.sql`을 운영 DB에 `accountant_scanner_inbox` 이름으로 적용했다. 운영 이력 버전은 `20261127064659`이며 원본 SHA256은 `250aebe270b8357ee6be6498e8fcf59e9bce1549a605cc9660e8222949b63ae4`이다. 기존에는 준비 안내만 표시하던 경리 화면이 정상 목록 응답을 확인하면 업로드를 활성화한다.

- 상사별 비공개 `snote-scanner-inbox` 버킷과 별도 저장 테이블을 사용한다. 익명·로그인 사용자의 직접 테이블/Storage 접근을 차단하고 기존 활성 경리·관리자 및 세션 검사를 재사용한다.
- 스캐너 앱에서 저장한 JPG·PNG·WebP 이미지를 선택하거나 끌어놓아 등록한다. 한 번에 최대 10장, 장당 5MiB를 지원한다. 보기·다운로드·삭제와 실패 후 재시도를 제공한다.
- 이 기능은 스캐너 장치를 직접 제어하지 않는다. 기존 차량 서류나 운영 서류에 자동 첨부하거나 덮어쓰지 않는다.

운영 스키마·버킷·함수·ACL·정책·인덱스·컬럼·제약을 로컬 검증 기준과 대조했다. PostgreSQL 버전별 별도 NOT NULL 제약 표현은 정규화하되 컬럼 nullable 값은 정확히 비교했다. 기존 함수 290개의 정의 해시·설정·ACL은 전부 동일하며 새 공개 함수는 서비스 전용 dispatcher 하나뿐이다. 적용 후 보안 advisory에 스캐너 관련 신규 지적은 없다. 기존 경고는 이번 범위에서 변경하지 않았다. 관련 권한 점검 기준은 [Supabase 보안 검사](https://supabase.com/docs/guides/database/database-linter)와 [비공개 버킷](https://supabase.com/docs/guides/storage/buckets/fundamentals)이다.
