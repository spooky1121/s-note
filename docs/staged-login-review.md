# 2단계 로그인·최초 사용 검토

기준 main은 `6a569c5b45f3239ec82898871f66cbd8a2526b08`(v2.183)이다. 1단계 데이터·권한 검증과 추가 신규 등록 검증을 마친 `6b1c73c` 위에서 작업했다. 독립 검증 당시 로그인 구현은 `26b5b84844262d14e6ec7fa6cb139c011a473b98`이며, 검토 브랜치에 가져온 대응 커밋은 `5192caf`다. 이 기록은 검토용이며 병합·배포나 운영 설정 변경을 수행하지 않았다.

## 변경과 유지

- 공개 차량 분류 파일·회사 차종 UI는 차량 등록/상세의 최초 사용 시 불러온다. 회사별 차종 조회도 로그인 직후 자동으로 실행하지 않는다. 공개 manifest 카탈로그와 비공개 회사별 추가 목록은 별도로 유지한다. 회사별 추가 목록은 기존 reset이 동기적으로 비우고, 현재 회사·사용자·조회 세대가 달라지면 조회 함수도 빈 배열을 반환한다.
- 경리 서류 업무의 양식 좌표·도장 렌더러·업무 모듈, 소득정산 부모 모듈, 회사 로고/도장 로더는 최초 사용 시 불러온다. 회사 이미지의 프로필·상사 설정·문서 공용 진입점과 기존 무효화/디코딩 처리는 유지한다.
- OCR 엔진은 원래부터 실제 이미지 분석 시에만 불러오므로 재구현하지 않았다. 인증, 활성 소속·역할 확인, 금융 잠금, idle/session 보호, 계좌 확인, 고객 서명 모듈과 판매 검증은 계속 초기 진입에 필요한 경로에 둔다. 문서 viewport도 기존 편집·인쇄 lifecycle을 위해 유지한다.
- 로그인에는 기본 회사 정보와 소속·권한을 확인한다. 문서용 회사 정보는 사용자 객체·client 객체·회사 ID·로그인 조회 세대·현재 화면에 결합하여 최초 견적서/계약서/인수증/경리 서류를 열기 전에 확인한다. 확인 실패 시 빈 회사 양식으로 진행하지 않는다. 회사 설정 조회·저장과 프로필 적용은 문서 정보 캐시를 무효화하여, 먼저 시작된 옛 응답이 새 저장 ACK를 덮어쓰지 않게 한다.
- 같은 회사·조회 context·client에서 동시에 요청하는 회사 차량 조회는 한 실행으로 합친다. 로그인 때 이미 확인한 동일 context의 이율 목록은 회사 차량을 읽을 때 재사용한다. 명시적인 새로고침·금융 설정 저장·공유 변경의 강제 재조회는 유지한다.
- 1단계의 인증된 금융 snapshot, CAS, 복구 hash, 공용 캐시 교차 회사 보호와 v2.183의 삭제 고객 출력 보호는 유지한다. 새 DB 스키마·정책·권한이나 운영 데이터를 변경하지 않았다.

## 같은 조건의 가상 측정

실제 로그인 운영 환경은 측정하지 않았다. 아래 값은 모든 Auth/DB/RPC 요청을 가상 응답으로 차단하고 요청마다 150ms를 고정한 Chromium 실험이다. 1440px와 390px의 새 브라우저 context를 각 3회 실행하며 로그인 클릭부터 인증 ACK, 소속·회사 확인, 필수 데이터, 금융 잠금·세션 정책, 화면이 실제로 조작 가능해지는 프레임까지 기록한다. 기준/변경본을 순차 실행하고 각 단계의 중앙값을 비교한다. CPU 공유에 따른 시간 변동이 있으므로 운영 속도 개선율로 해석하지 않는다.

| 누적 단계(중앙값) | PC 변경 전 | PC 변경 후 | 390px 변경 전 | 390px 변경 후 |
|---|---:|---:|---:|---:|
| 인증 ACK | 186.3ms | 180.0ms | 166.2ms | 171.8ms |
| 활성 소속·회사 확인 | 512.2ms | 515.1ms | 488.2ms | 501.5ms |
| 필수 데이터 확인 | 755.8ms | 793.2ms | 727.7ms | 815.4ms |
| 금융 잠금·세션 정책 확인 | 1,005.8ms | 1,058.0ms | 972.9ms | 1,147.2ms |
| 첫 업무 화면 조작 가능 | 1,084.0ms | 1,114.6ms | 1,111.4ms | 1,311.8ms |

첫 조작 가능 시간의 3회 범위는 PC 변경 전 1015.4~1093.5ms, 변경 후 1074.4~1216.5ms, 390px 변경 전 1083.4~4288.8ms, 변경 후 1217.7~1429.1ms였다. 이번 고정 지연 실험에서 로그인 클릭 이후 시간의 개선은 입증하지 못했다. 초기 자산·부가 요청 감소와 시간 개선 여부를 구분한다.

초기 요청 수는 회사 차종·카탈로그 관련 **7 → 3개**, 문서/인쇄 관련 **15 → 8개**, OCR 엔진은 **0 → 0개**였다. 요청 수에는 해당 기능의 CSS도 포함한다. 제거한 것은 최초 사용 전의 JS/분류 데이터 요청이다. 남은 스타일·서명·계좌·viewport 로직은 그대로 유지한다. 회사 메타데이터 조회는 초기 회사 기본정보 조회 1회만 수행하고, 문서 첫 사용 시 별도 확인한다.

가상 관리자가 로그인한 뒤 재고금융 화면을 여는 실제 UI에서는 이율 목록 조회가 **2 → 1회**로 줄었고 회사 차량 조회는 1회였다. 동시 회사 조회 두 번도 실행 1회로 합쳐지는 것을 따로 검증했다. 이 수치는 서버 운영 트래픽을 관측한 값이 아니다.

## 검증

- 정상 로그인 10그룹: 독립 브라우저/같은 브라우저의 두 탭, 잘못된 비밀번호·재시도·기억된 로그인, 현재 세션 로그아웃, 기존 idle 만료, 지연·실패한 사진 요청, 로그아웃 뒤 지연 응답, 필수 인증·소속 확인, 비활성 소속 차단.
- 최초 사용 9그룹: 필수 모듈 유지, 카탈로그·신규 등록 최초 로드, 회사 정보 동시 조회 합치기, 차량 닫기/메뉴 이동/회사 전환 후 늦은 계약서 열림 차단, 회사 정보 권한 실패, 회사 조회/이율 중복 제거, 경리 첫 업무 화면, 이전 회사 차종이 새 회사 조회 보류 중 노출되지 않음, 새 프로필 저장 ACK를 지연 응답이 덮어쓰지 않음.
- 기존 신규 등록 16그룹: 1440/390/320px, 저장 ACK 전 성공 표시 없음, 실패·응답 유실·재시도, 중복 방지, 금융 날짜/비용, 기존 선택·OCR 내용, 상세 재편집, 미완료 닫기.
- 계좌 8그룹, 회사 이미지/도장 6그룹, 프로필 회사 로고 6그룹, 문서 아이콘 4규격, PC/모바일 계약서·인수증 실제 A4 PDF 4건, 삭제 고객 출력과 정상 고객·지연 응답 4그룹.
- 실제 가상 두 탭의 금융 snapshot/CAS/회사 전환 보호 1440/390px, 기존 idle/session 브라우저 회귀, 금융 복구·idle 복구·금융 사용액·회사 범위·금융 잠금·판매 화면 복귀·고객 서명 단위 회귀 통과. 1단계의 갱신된 회사 snapshot fixture를 사용했다.
- JS/inline script 구문과 diff 공백 검사 통과. 모든 고객·차량·상사·계좌·이미지는 가상 자료이며 운영 요청·문자 발송·금융 실행은 하지 않았다.

## 운영에서 확인할 항목

승인 후 별도 운영 검증에서는 같은 기기·브라우저·네트워크·권한의 가상 시험 계정으로 초기 캐시 유무를 구분하고 각 3회 이상 측정해야 한다. Auth 응답, 활성 소속과 회사 조회, 필수 데이터·잠금 정책, 첫 업무 버튼이 조작 가능한 시점을 구분한다. 경리의 첫 서류 업무와 딜러의 첫 대시보드는 서로 다른 업무 화면이므로 별도로 측정한다. 이번 시간 측정은 딜러의 가상 대시보드 기준이다. 경리 첫 화면은 최초 사용 동작·권한 가드를 검증했으며 운영 지연 시간은 측정하지 않았다.

실제 Supabase/Cloudflare 네트워크 지연, 운영 계정의 실제 로그인, 원격 DB 부하, 물리 모바일 기기의 입력·키보드 동작은 이 검토의 운영 검증 결과로 표시하지 않는다.
