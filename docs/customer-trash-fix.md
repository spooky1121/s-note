# 고객관리 삭제·휴지통 수정

기준은 기존 검토 커밋 `65e7e06`이며 작업 브랜치는 `codex/customer-trash-v2184`다. 앞선 단계별 개선을 보존했으며 main 병합·운영 배포·운영 데이터/설정 변경은 하지 않는다.

## 원인과 변경

식별번호를 비동기로 확인한 뒤 고객 목록이 다시 그려지면 원래 삭제 버튼이 교체된다. 삭제 확인창은 그 버튼의 DOM 연결 상태를 기준으로 유지되어, 확인 도중 버튼이 교체되면 삭제 요청 없이 취소되었다. 기준 코드에서 PC/390px 모두 같은 현상을 재현했고, 해당 고객은 남으며 휴지통 요청은 0건이었다.

확인은 같은 계정·상사·목록 화면과 선택 고객을 기준으로 유지한다. 확인부터 요청 완료까지 중복 실행을 막고, 새로 그려진 삭제 버튼에도 처리 중 상태를 적용한다. 기존 서버 휴지통 RPC, 수정 시각/복원 세대의 동시 수정 검사, 세션·상사·소유자 권한 확인은 그대로 사용한다.

서버가 해당 고객의 휴지통 이동을 확인하면 현재 목록에서 그 고객만 즉시 제외한다. 검색창·정렬·카드/목록 모드를 유지하고 고객 수·빈 목록·마지막 페이지를 다시 계산한다. 식별번호의 늦은 응답은 삭제한 고객을 되살리거나 검색용 식별번호를 남기지 않는다. 취소·실패에는 행을 제거하지 않는다. 차량과 첨부 파일은 삭제하지 않는다.

독립 리뷰에서 이전 삭제 응답이 새로 연 목록의 복원된 고객을 숨길 수 있는 추가 경합을 발견했다. 요청 당시 목록 토큰과 조회 세대를 응답 반영에도 사용하여, 늦은 응답은 새 목록을 제거하거나 무효화하지 않도록 보완했다. 기존 고객 복원의 무효화·서명 보호는 유지한다. 수정된 목록 모듈에는 새 자산 캐시 주소를 적용했다.

## 검증

모든 고객·계정·상사·차량·파일·서버 응답은 가상 자료이며 SQL은 격리된 로컬 PostgreSQL에서 실행한다.

- 고객 목록 단위 16건: 기존 검색/식별번호 보호, 비동기 식별번호와 삭제, 검색·보기 유지, 마지막 페이지 정리, 이전 목록 토큰 차단.
- 고객 레코드·계약서 서명 단위 20건.
- 기존 휴지통 SQL 74건: 상사/소유자 분리, 보관·복원, 동시 수정·오래된 저장 보호.
- 기존 고객 목록 브라우저 9그룹: 1440/1024/390/320px, 보기·검색·정렬·페이지·권한·화면 수명.
- 관련 기존 휴지통 브라우저 7그룹: 고객 동시 수정/복원 세대, 판매/인수증 저장 보호, 지연 세션과 계정 변경, 늦은 응답, 차량/파일 복원.
- 새 실제 고객 삭제 UI 22개 시나리오: 1440/390px 각각 11개. 식별번호 조회·검색·정렬 중 확인, 처리 중 버튼 교체, 중복 클릭, 취소/서버 거부/버전 충돌, 계정/화면 변경, 새로 복원한 목록에 대한 이전 응답, 즉시 행·고객 수·페이지 갱신과 휴지통 표시를 확인했다. 삭제 함수를 mock하지 않고 실제 확인창·핸들러·고정 세션 RPC를 실행했다.

최종 검증 전후 `index.html`과 `assets/customer-list.js`의 SHA256이 동일하다. 문법·공백 검사도 통과했다.

재사용 브라우저 fixture의 고정 RPC 주소와 오래된 합성 토큰 기대값을 현재 가상 세션에 맞췄다. 기존 본문 assertion은 유지했다. 전체 휴지통 suite는 고객 경로에 들어가기 전 선택적인 설정 RPC를 기존 공용 fixture가 지원하지 않아 중단되었으며, 이를 전체 통과로 기록하지 않는다. 고객과 관련된 위 5개 함수를 같은 assertion으로 따로 실행하여 7그룹을 통과했다.

새 실제 고객 삭제 UI와 최종 해시 증적은 작업 환경 `/workspace/work/customer-trash/`, 추가 단위·기존 회귀 결과는 `/workspace/work/customer-trash-v2184/`에 보관한다. 운영 계정에서의 실사용은 검증하지 않았으며 운영 DB 스키마·정책 변경도 없다.
