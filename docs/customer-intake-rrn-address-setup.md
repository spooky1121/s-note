# 고객 모바일 주민번호·카카오 주소 검색 적용

v2.12에서 고객의 문자 인증 후 입력 화면에 주민등록번호 입력과 카카오 주소 검색을 추가했습니다. 주소 검색에는 별도 카카오 앱 키를 등록하지 않습니다. 기본주소를 검색해 선택하면 자동 입력되고, 상세주소는 고객이 직접 입력합니다. 등기받을 주소도 별도로 검색하거나 ‘위 주소와 동일’을 사용할 수 있습니다.

## 기존 운영 환경에 추가할 설정

1. Supabase SQL Editor에서 [주민번호 암호문 보관·조회 권한 SQL](../supabase/migrations/202611010003_customer_intake_rrn.sql) 파일을 **처음부터 끝까지 실행**합니다. 기존 고객 접수 SQL 0001·정리 예약 SQL 0002가 먼저 적용되어 있어야 합니다. 이 SQL은 상사의 주민번호 수집 설정을 자동으로 켜지 않습니다.
2. Cloudflare Pages → 프로젝트 → Settings → Variables and Secrets → Production에 **Secret**을 하나 추가합니다. 이름은 `CUSTOMER_INTAKE_RRN_KEY`, 값은 암호학적으로 무작위 생성한 **64자리 16진수**입니다. 신뢰할 수 있는 로컬 터미널에서 `openssl rand -hex 32`로 생성하거나, 비밀번호 관리자의 암호학적 난수 생성 기능을 사용합니다. 기존 OTP Secret과 다른 값으로 만들고, Cloudflare Secret 입력란에만 저장합니다. 키를 GitHub·HTML·채팅에 올리지 않습니다.
3. 기존 상사 설정 `zc_companies.rrn_enabled`가 활성 상태인지 확인합니다. 이 설정은 주민번호 처리에 관한 법적 근거를 확인한 상사만 사용하는 기존 설정입니다. 일반 개인정보 동의나 문자 인증만으로 주민번호 수집 근거가 생기지는 않습니다. 해당 업무의 구체적인 목적·근거와 고객 안내를 확인한 후 운영합니다. 활성화되지 않은 상사에서는 주민번호를 받지 않으며, 이름·주소 접수와 문자 발송은 계속 사용할 수 있습니다.
4. 설정 저장 후 v2.12 전체 파일로 다시 배포합니다. 새 `address-search.html`, `assets/address-search.*`, `_headers`, `functions/api/customer-intake.js`도 함께 배포되어야 합니다. `index.html`만 교체하면 고객 화면과 서버 기능은 적용되지 않습니다.
5. 운영 주소의 `/api/customer-intake`에서 기존 `configured: true`와 함께 `rrnConfigured: true`를 확인합니다. `rrnConfigured`는 암호화 키 형식 검사 결과입니다. DB SQL과 상사별 활성화 여부는 실제 고객 입력 화면에서 확인합니다.

이 Secret은 주민번호만 별도로 암호화하는 키입니다. 등록하지 않아도 기존 문자 발송·일반 고객정보 접수는 계속 작동합니다. Preview 환경을 사용한다면 해당 환경에도 별도로 설정합니다.

## 입력·보관·불러오기

- 주민번호는 상사 설정과 서버 암호화 키가 준비된 경우에만 입력할 수 있는 선택 항목입니다. 앞 6자리와 뒤 7자리를 나누어 입력하며, 뒷자리는 가려서 표시합니다. 입력하는 경우 별도 안내 확인이 필요합니다.
- 서버는 번호를 AES-256-GCM으로 암호화해 접수함의 별도 비공개 필드에 저장합니다. 이름·주소가 있는 일반 고객 JSON, 목록 자동 조회, 브라우저 저장소에는 주민번호 평문을 넣지 않습니다.
- 해당 차량을 담당하는 로그인한 직원이 **입력정보 불러오기**를 누를 때만 별도 권한 확인과 복호화를 거쳐 판매 입력칸에 반영합니다. 기존 번호를 덮어쓰는 경우 확인하며, 자동 조회로 복호화하지 않습니다. 계약서 저장은 기존 서버 주민번호 저장 기능을 이용합니다.
- 접수함의 번호는 접수 후 최대 30일간 조회할 수 있습니다. 기존 0002 SQL의 정리 작업이 접수 내역과 함께 삭제합니다. 상사 비활성화·접수 취소·권한 변경 시 조회를 거절합니다. 계약서·고객관리로 따로 저장한 기록은 접수함 정리 대상이 아닙니다.
- 주소 검색은 고객 화면과 분리한 검색창에서 실행합니다. 카카오 검색 코드에 주민번호·문자 인증번호·접수 토큰을 전달하지 않습니다. 검색 결과인 주소만 고객 화면으로 돌려보냅니다.

암호화 키를 지우거나 교체하면 기존 키로 보관한 번호는 복호화할 수 없습니다. 기존 접수함의 번호가 모두 보관기간 만료로 삭제되거나 별도 처리될 때까지 같은 키를 안전하게 유지합니다. 키 변경이 필요한 경우 기존 자료 처리 계획을 먼저 정합니다. OTP Secret 교체는 이 암호화 키에 영향을 주지 않습니다.

## 운영 확인

운영자가 관리하는 테스트 휴대폰에서 기존 문자 인증을 진행한 뒤 기본주소 검색 → 상세주소 입력 → 등기주소 동기화 및 별도 검색 → 제출 → 담당자 불러오기를 확인합니다. 검색이 진행되지 않으면 검색창 안의 **새 창에서 주소 검색**을 눌러 이용할 수 있습니다. 팝업이 차단되면 브라우저 설정을 확인하거나 주소를 직접 입력합니다. 주소 검색 취소나 로딩 실패 후에도 직접 입력은 가능합니다. 실제 고객 주민번호를 개발·테스트에 사용하지 않습니다.

카카오의 현재 검색 호스트는 `postcode.map.kakao.com`, SDK 호스트는 `t1.kakaocdn.net`입니다. [공식 도메인 안내](https://github.com/kakao-postcode/kakao-postcode-QnA/issues/1560)와 [CDN 변경 공지](https://github.com/kakao-postcode/kakao-postcode-QnA/issues/1562)를 기준으로 고객 페이지와 주소 검색 페이지의 CSP를 분리했습니다. 개발 환경에서는 카카오 실서비스 접속이 프록시에서 차단되어 모의 SDK로 주소 선택·입력 및 브라우저 격리를 검증했습니다. 실제 검색·새 창 동작은 운영 배포 후 휴대폰에서 확인해야 합니다.

입력란이 비활성 상태라면 순서대로 새 SQL 적용, Cloudflare Secret 이름과 형식, 설정 저장 후 재배포, 해당 상사 `rrn_enabled` 설정을 확인합니다. 번호를 불러올 때 실패하면 기존 입력칸을 유지합니다. 조회 오류를 해결하기 위해 문자를 다시 보낼 필요는 없습니다.
