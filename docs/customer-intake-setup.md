# 고객 휴대폰 입력·문자 인증 운영 절차

이 기능은 고객에게 전용 링크를 문자로 보내고, 해당 휴대폰으로 받은 인증번호를 확인한 뒤 고객정보를 서버에 접수합니다. 고객의 **휴대폰 사용 여부**를 확인하는 방식이며, 통신사 실명 본인확인이나 전자서명을 대신하지 않습니다.

## 1. 이용 흐름

1. 담당 딜러가 차량을 저장하고 **차량 상세 → 판매 진행 → 휴대폰으로 고객정보 받기**를 엽니다.
2. 받을 휴대폰 번호를 확인하고 **고객 입력 요청**을 누릅니다. 서버에 저장된 담당자 본인의 차량 정보가 사용됩니다.
3. 고객이 문자 링크에서 차량명·차량번호·연식·주행거리·안내 판매가격을 확인합니다.
4. 고객이 **인증번호 받기**를 누르면 처음 지정한 휴대폰으로만 인증번호가 전송됩니다. 고객 화면에서 수신 번호를 바꿀 수 없습니다.
5. 인증 후 이름·주소·등기 주소와 필요한 경우 이전비 환급계좌를 입력하고 동의 후 제출합니다.
6. 서버 저장이 성공하면 고객에게 접수 완료가 표시되고, 담당자 판매 화면에 제출 상태가 표시됩니다.
7. 담당자가 **입력정보 불러오기**를 눌러 내용을 확인한 뒤 계약서 또는 인수증을 엽니다. 기존 판매 흐름을 통해 고객관리와 문서에 반영됩니다.

고객 제출은 먼저 별도 서버 접수함에 저장됩니다. 기존 고객 기록·계약금액·특약사항을 즉시 덮어쓰지 않습니다. 고객이 제출하고 담당자가 아직 불러오지 않은 경우에도 서버에는 제출 내역이 남습니다.

## 2. SOLAPI 준비

1. [SOLAPI](https://solapi.com/)에 계정을 만들고 문자 서비스를 사용할 수 있도록 설정합니다.
2. **발신번호 관리**에서 실제 사용할 번호를 등록하고 승인 상태를 확인합니다. 사업자 계정에서 요구하는 확인 절차는 서비스 안내를 따릅니다.
3. API Key와 API Secret을 발급합니다.
4. 문자 잔액과 메시지 발송 권한을 확인합니다. 링크 안내는 LMS, 인증번호는 SMS를 사용합니다. 건당 요금은 SOLAPI의 현재 요금표를 확인하세요.

발신번호 미승인, 잔액 부족, API 권한 오류가 있으면 문자 전송이 실패합니다. 발송 접수와 실제 고객 수신은 다르므로 SOLAPI 발송 내역도 함께 확인합니다.

## 3. Supabase DB 적용

연결 프로젝트의 [SQL Editor](https://supabase.com/dashboard/project/rmlycycleuscfqywbihj/sql/new)에서 새 쿼리를 열고 아래 파일을 순서대로 **전체 실행**합니다. 파일 중간의 함수 본문만 선택하지 마세요.

1. [고객 입력 DB·권한·인증 상태 처리 SQL](../supabase/migrations/202611010001_customer_intake.sql)
2. [보관기간 경과 자료 정리 예약 SQL](../supabase/migrations/202611010002_customer_intake_cleanup.sql)

이 기능에는 기존 `zc_companies`, `zc_members`, `zc_datasets` 테이블이 있는 S-NOTE 프로젝트가 필요합니다. 기존 고객·차량·문자열 데이터나 역할을 새로 만들거나 덮어쓰는 용도의 SQL이 아닙니다.

고객용 익명 계정에는 테이블 조회·쓰기 권한을 주지 않습니다. 담당자는 로그인한 자신의 차량 요청만 만들고 확인합니다. 고객용 서버 작업은 Cloudflare에 보관한 전용 서버 키로 제한된 저장 함수만 호출합니다.

고객의 휴대폰 제출 내역은 30일 후 정리하고, 만료된 미제출 링크는 별도로 정리합니다. 두 번째 SQL로 Supabase Cron 정리 작업을 등록하고, Cron 화면에서 작업이 활성 상태인지와 실행 기록을 확인하세요. 담당자가 계약서·고객관리로 반영한 기록은 이 접수함 정리 작업의 삭제 대상이 아닙니다.

## 4. Cloudflare Pages 설정

**Workers & Pages → s-note → Settings → Variables and Secrets → Production**에 설정합니다. 테스트 배포에서도 사용할 경우 Preview 환경은 별도로 설정합니다.

| 이름 | 종류 | 설정 내용 |
|---|---|---|
| `SUPABASE_URL` | 변수 | 기존 앱과 같은 Supabase 프로젝트 URL |
| `SUPABASE_PUBLISHABLE_KEY` | 변수 | 같은 프로젝트의 공개 publishable key |
| `SUPABASE_SERVICE_ROLE_KEY` | 암호화된 Secret | 같은 프로젝트의 서버 전용 `service_role` JWT 키 |
| `CUSTOMER_INTAKE_PUBLIC_ORIGIN` | 변수 | 고객이 실제 접속할 운영 HTTPS 주소. 경로나 `#` 없이 입력. 예: `https://s-note.pages.dev` |
| `SOLAPI_API_KEY` | 암호화된 Secret | SOLAPI API Key |
| `SOLAPI_API_SECRET` | 암호화된 Secret | SOLAPI API Secret |
| `SOLAPI_SENDER` | 변수 | 승인된 발신번호, 숫자만 입력 |
| `CUSTOMER_INTAKE_OTP_SECRET` | 암호화된 Secret | 인증번호 해시용, 충분히 긴 무작위 문자열(32자 이상) |

Supabase 서버 키는 **Settings → API Keys**에서 해당 프로젝트의 `service_role` JWT 키를 확인합니다. 공개 publishable/anon key와 다른 키입니다. 서버 키와 문자 API Secret은 `index.html`, 고객 페이지, GitHub 또는 채팅에 붙여 넣지 말고 Cloudflare Secret 입력란에 저장합니다.

인증번호 해시용 Secret은 비밀번호 관리자에서 긴 무작위 값으로 만들거나 신뢰할 수 있는 로컬 환경에서 `openssl rand -hex 32`로 생성해 Secret 입력란에 저장합니다. 값을 공유하지 않습니다. 이 Secret을 바꾸면 진행 중인 인증번호는 다시 받아야 합니다.

여기의 설정 위치는 **실제 웹사이트를 실행하는 Cloudflare Pages**입니다. Codex 작업 환경에만 변수를 입력해도 운영 사이트에 자동 전달되지는 않습니다. 설정을 저장한 후 해당 환경으로 다시 배포합니다.

## 5. 배포 및 개통 확인

1. 위 DB SQL 두 개와 Cloudflare 설정을 완료합니다.
2. GitHub의 기능 커밋을 포함한 최신 버전으로 Pages를 배포합니다. `index.html`뿐 아니라 `customer.html`, 새 `assets`·`functions` 파일과 `_headers`도 함께 배포되어야 합니다. GitHub 체크만으로 확정하기 어려우면 Cloudflare 프로젝트의 배포 화면에서 사용 중인 커밋을 확인합니다.
3. 운영 주소의 `/api/customer-intake`에 접속해 `service`가 `snote-customer-intake`, `configured`가 `true`인지 확인합니다. 이 표시는 필요한 서버 설정 유무이며 실제 문자 수신이나 DB 함수 적용까지 보증하지 않습니다.
   `configurationIssues`에는 문제가 있는 설정 이름과 사유만 표시되며 키 값은 표시되지 않습니다. `originMatches`가 `false`이면 현재 접속 주소와 `CUSTOMER_INTAKE_PUBLIC_ORIGIN`을 일치시킵니다. 설정을 확인한 주소와 판매 화면의 주소도 같아야 합니다.
4. 로그인한 담당자 본인의 저장된 차량에서 판매 진행을 엽니다. 관리자도 다른 담당자 차량에 대신 요청하지 않고 해당 담당자 계정으로 진행합니다.
5. **운영자가 직접 관리하는 테스트 휴대폰**으로 입력 요청을 한 번 보냅니다. 이 단계부터 실제 문자 비용이 발생합니다.
6. 휴대폰에서 링크를 열고 인증번호를 받아 정보를 제출합니다. 이 과정에서 휴대폰 사용 확인과 개인정보 처리 동의를 직접 확인합니다.
7. 담당자 화면에서 새로고침 또는 자동 조회로 제출 완료를 확인하고, 불러온 정보로 계약서·인수증의 고객 정보가 맞는지 확인합니다.
8. 다른 기기에서도 같은 담당자 계정으로 로그인해 제출 내역이 조회되는지 확인합니다.
9. 만료·취소한 링크와 사용한 인증번호의 재사용이 거절되는지 확인합니다. 처음 시험한 링크와 제출 내역은 운영 방침에 맞게 정리합니다.

설정이 빠져 있거나 저장이 실패했을 때 임시 인증번호나 브라우저 저장만으로 완료 처리하지 않습니다. 개통 전에는 고객에게 실제 요청을 보내지 않습니다.

## 6. 고객 및 담당자 안내

- 링크는 발급 후 24시간 유효합니다. 새 요청을 만들면 같은 담당자·차량의 기존 미제출 링크는 취소됩니다.
- 인증번호는 5분 유효하며 재발송은 60초 후 가능합니다. 링크당 최대 5회 발송, 인증번호당 최대 5회 오류 제한이 적용됩니다. 같은 휴대폰의 시간당 발송도 제한합니다.
- 인증 후 입력 시간은 최대 30분이며 원래 링크 만료시간을 넘지 않습니다. 시간이 지나면 다시 문자 링크에서 인증합니다.
- 접수 완료된 링크는 다시 수정할 수 없습니다. 고객이 내용을 바꾸려면 담당자가 새 입력 요청을 만듭니다.
- 고객 페이지를 닫거나 새로고침해 입력 중인 화면이 사라진 경우 원래 문자 링크에서 다시 시작합니다. 정보와 인증 토큰을 휴대폰 브라우저 저장소에 보관하지 않습니다.
- 이름·주소는 고객이 입력한 값입니다. 이 인증은 고객이 해당 휴대폰을 사용할 수 있는지 확인하며 실명이나 계좌 예금주 일치 여부를 보증하지 않습니다.
- 이름·확인된 전화번호·주소·선택한 등기 주소를 접수합니다. 환급계좌는 선택 사항이고 입력할 때 별도 동의가 필요합니다. 주민번호나 신분증 사진을 이 휴대폰 입력 페이지에서 받지 않습니다.
- 문자 수신까지 지연될 수 있습니다. 접수 여부가 불확실한 경우 즉시 여러 번 보내지 말고 발송 내역을 먼저 확인합니다.

## 7. 오류 확인

| 증상 | 확인할 항목 |
|---|---|
| 문자 설정이 필요하다는 안내 | Cloudflare Production/Preview의 설정과 재배포 여부. 전화번호는 미리 입력할 수 있고, 설정 확인 후 새로고침하면 발송이 활성화됩니다. OTP Secret은 앞뒤 공백을 제외하고 32자 이상이어야 합니다. |
| DB 준비 안내 또는 저장 함수 오류 | 첫 번째 SQL 전체 실행, 기존 프로젝트 테이블, 동일 프로젝트 URL/키 |
| 서버의 Supabase 연결 설정 안내 | Cloudflare의 `SUPABASE_SERVICE_ROLE_KEY`에 동일 프로젝트의 서버 전용 legacy service_role JWT 키를 사용했는지 확인 후 재배포 |
| 설정은 정상인데 문자 요청 결과를 확인하지 못했다는 안내 | v2.11 이후의 `functions/api/customer-intake.js`까지 포함해 재배포했는지 확인. 구버전의 Cloudflare 호출 옵션 호환성 문제를 수정했습니다. 요청을 반복하지 말고 SOLAPI 발송 내역을 먼저 확인합니다. |
| 문자 접수 실패 | SOLAPI 발신번호 승인, 잔액, API 키 권한, 발송 내역 |
| 오래된 링크·취소된 링크 | 담당자가 최신 요청을 만들고 있는지, 원래 링크의 유효시간 |
| 인증번호 오류·횟수 초과 | 최신 문자 사용 여부, 5분·5회 제한, 60초 후 새 번호 요청 |
| 제출 중 통신 오류 | 입력 화면의 재시도로 접수 결과 확인. 서버가 성공을 확인하기 전에는 완료로 보지 않음 |
| 고객정보가 기존 계약서와 다름 | 판매 진행에서 제출 정보를 불러온 뒤 현재 내용을 확인하고 문서를 다시 열었는지 |
| 30일 정리 작업 확인 | Supabase Cron의 작업 활성 상태와 최근 실행 결과 |

개발 중 검증은 가짜 문자 응답과 분리된 테스트 DB로 수행합니다. 실제 문자 전송·운영 DB 적용·발신번호 승인은 운영 설정과 개통 시험 단계에서 확인합니다.

## 8. 코드 변경 후 검증

Node.js 24 환경에서 아래 명령은 외부 서비스를 호출하지 않습니다.

```sh
node tests/customer-intake.test.mjs
node tests/customer-records.test.mjs
```

추가로 분리된 PostgreSQL 엔진에서 DB 권한·인증 횟수·유효기간·중복 제출·자료 정리를 검증했고, 브라우저에서는 실제 API와 분리된 DB를 연결해 고객 제출부터 담당자 불러오기·계약서 반영까지 확인했습니다. 운영 개통 시험은 위 5절을 따릅니다.

실제 Cloudflare 실행 엔진의 호환성은 [workerd 회귀 테스트](../tests/customer-intake.workerd.cjs)로 별도 확인합니다. 파일 상단의 안내대로 Miniflare와 undici를 저장소 외부에 설치한 뒤 실행합니다. 모든 외부 요청을 모의 응답으로 처리하며 실제 문자나 운영 DB를 호출하지 않습니다. 정적 Pages 배포 방식을 유지하기 위해 이 테스트를 위한 루트 `package.json`은 추가하지 않습니다.
