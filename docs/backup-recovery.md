# S-NOTE 백업과 재해 복구

## 현재 상태와 범위

이 변경은 **운영자용 암호화 백업·검증·로컬 추출 도구**를 추가한다. 브라우저 관리자 권한으로 전체 상사 데이터를 내려받는 API나 버튼은 만들지 않는다. 서비스 키는 프런트엔드에 넣지 않는다.

운영의 버킷·객체 수·용량과 마지막 성공 백업 시점은 승인된 비공개 운영 기록에서 확인한다. 공개 소스에는 운영 재고나 실제 고객 자료를 넣지 않는다. 재고 목록만으로 백업이 완료되었다고 판단하지 않는다.

**이 작업에서 실제 운영 전체 백업, 원격 사본 생성, 운영 복구, PITR 활성화, 유료 요금제 변경, 예약 실행, 자동 삭제는 수행하지 않았다.** 기존 Supabase 백업/PITR의 활성 여부와 마지막 성공 시점도 확인되지 않았다. 운영 자료를 이 저장소나 테스트 파일에 복사하지 않았다.

기존 휴지통은 차량·고객·첨부의 실수 삭제를 복원하지만 원본 DB/Storage가 소실되면 함께 사라진다. 차종 연구자료의 정적 백업도 운영 업무자료를 대체하지 않는다. Supabase의 DB 백업은 Storage의 실제 파일 바이트를 포함하지 않는다.

### 보관 대상

- `pg_dump`의 전체 DB 사용자 스키마, 테이블 데이터, 시퀀스, 함수, 트리거, 인덱스, RLS 및 권한. 테이블·스키마 허용 목록으로 범위를 줄이지 않는다.
- 차량·비용·판매·소득정산과 월정산(`zc_datasets`), 고객·계약·서명(`zc_customers`), 회원·상사·미디어 및 레거시 테이블.
- `snote_private` 휴지통·공유·프로필, 운영자·지원·차종·환경설정 비공개 스키마, `zc_private`의 기존 암호문/키, Auth 데이터 등 DB에 실제 존재하는 내용.
- 모든 표준 Storage 버킷의 현재 객체. 미디어에 연결되지 않은 파일도 누락하지 않는다. DB 목록과 각 파일의 크기, ETag, SHA-256 및 버킷 설정을 함께 보관한다.
- 역할의 이름·속성·멤버십·DB별 설정 목록. 이 JSON은 실행 가능한 글로벌 역할 복원 SQL이 아니며, `pg_dump`는 역할 자체를 생성하지 않는다. 대상별 역할 생성과 권한 대조는 별도로 필요하다. **PostgreSQL 역할 비밀번호는 보관하지 않지만, 전체 DB에는 Auth 사용자 인증 자료 등 민감한 데이터가 포함될 수 있다.** 따라서 백업 전체를 고도의 민감자료로 취급한다.

### 별도 보존 또는 확인이 필요한 대상

- Cloudflare Pages/Functions 소스와 배포 커밋, 환경변수 이름, DNS/도메인, Auth 공급자·메일·문자 설정, 사용자 지정 역할 및 외부 연동 설정.
- 외부 암호화 키 값. 특히 고객 식별정보 복호화에는 `CUSTOMER_INTAKE_RRN_KEY` 또는 기존 `CUSTOMER_INTAKE_OTP_SECRET`에서 파생한 키가 필요하다. 키와 설정 값은 별도의 승인된 비밀 저장소에 보존해야 하며 이 문서·Git·로그·백업 파일 옆에 기록하지 않는다. DB Vault의 외부 루트 키 등 관리형 서비스 종속성도 별도 확인한다.
- 브라우저에만 남은 미동기화 입력, 체험용 계정 자료, IndexedDB 파일, 과거에 영구 삭제한 Storage 버전은 서버 백업으로 복구할 수 없다.
- 표준 Storage 외 Analytics/Vector 버킷은 지원하지 않는다. 해당 버킷이 존재하면 도구는 완료를 거부한다.
- 사용자 지정 역할 비밀번호, 인프라 설정, 업로드 중인 파일, 아직 생성되지 않은 전송 작업 대상은 자동으로 재구성하지 않는다.

## 구현된 보호 장치

`node scripts/snote-backup.mjs --help`

1. DB 연결은 명시한 프로젝트의 직접 연결 주소에만 허용한다. `verify-full` TLS, 읽기 전용 트랜잭션, 연결 15초 제한, 쿼리·작업 제한을 적용한다. 트랜잭션 풀러와 암묵적 libpq 서비스 설정은 허용하지 않는다.
2. `REPEATABLE READ READ ONLY` 트랜잭션의 `pg_export_snapshot()`을 `pg_dump --snapshot`에도 사용한다. 전체 DB와 파일 목록의 DB 시점을 맞춘다. 기존 역할의 읽기 권한이 부족하면 실패하며 권한을 자동 확대하지 않는다.
3. 생성 중인 DB 덤프를 `pg_restore --file=/dev/null`로 파싱한다. SQL을 실행하지 않고 압축된 덤프 내용을 끝까지 읽을 수 있는지 확인한다. **관리형 Supabase로 복구되는지는 이 검사만으로 증명되지 않는다.**
4. 실제 파일을 다운로드할 때 동일 프로젝트 HTTPS 주소만 사용하며 리디렉션을 거부한다. 스냅샷의 ETag가 없거나 달라지면 실패한다. 바이트 수와 단일 부분 MD5 ETag도 검사한다. 마지막에 Storage 목록/버킷 설정을 다시 비교하며 변경이 있으면 실패한다. 다운로드에 따라 달라질 수 있는 `last_accessed_at`만 비교에서 제외한다.
5. `zc_media`, 휴지통 `recycle_files`, 현재 `profile_avatars.file_path`의 참조가 Storage 목록에 존재하는지도 확인한다. 누락된 원본은 복구할 수 없으므로 성공으로 표시하지 않는다. 정상적으로 정리될 수 있는 `previous_path`는 필수 원본으로 취급하지 않는다.
6. DB 덤프와 파일은 평문 임시파일 없이 암호화한다. AES-256-GCM, 매 실행 무작위 salt/nonce, scrypt(N=65536, r=8, p=1), 순서가 인증되는 프레임, 암호화된 최종 파일별 SHA-256 목록을 사용한다. 최소 20자 암호를 요구하며 강한 무작위 암호를 권장한다. 암호는 복구에 필수이고 백업과 별도로 보관한다.
7. 모든 항목과 완료 레코드를 검증한 뒤에만 최종 파일명으로 게시한다. 누락·변조·잘못된 암호·중간 절단·재정렬·뒤에 붙은 데이터·이름 충돌을 거부한다. 기존 백업을 덮어쓰지 않는다.
8. 출력 상위 폴더는 실행 사용자만 접근할 수 있어야 한다. 새 파일은 `0600`, 추출 폴더는 `0700`으로 만든다. 기존 폴더 권한, DB 권한, 버킷 공개 여부는 바꾸지 않는다. 오류 로그에는 사용자 데이터·객체 경로·자격증명을 출력하지 않는다.

현재 캡처는 파일 8,000개와 DB 파일 목록 메타데이터 64MiB로 제한하며 DB/파일 스트리밍 전에 초과를 거부한다. 단일 최종 목록 프레임은 약 2MiB 제한이다. 대규모 확장으로 한도를 넘으면 실패하며 일부만 성공 처리하지 않는다. 데이터 바이트는 1MiB 단위로 처리한다.

## 운영 첫 실행 전 준비

1. 승인된 실행 컴퓨터와 비공개 출력 위치, 별도 사본의 목적지/수신자, 백업 담당자와 복구 담당자를 정한다. 백업을 공개 Git 저장소·웹 정적 디렉터리·일반 공유 드라이브에 두지 않는다.
2. 캡처와 평문 추출은 POSIX 권한을 검증하는 Linux/macOS에서만 지원한다. Windows에서는 NTFS ACL을 대신 보장할 수 없으므로 출력을 거부한다. Node.js 20 이상과 **DB 버전에 맞는 PostgreSQL 클라이언트** `psql`, `pg_dump`, `pg_restore`가 필요하다. 확인 당시 운영 DB는 PostgreSQL 17이었다. 이 도구는 소프트웨어나 CLI 최신판을 자동 설치하지 않는다.
3. 이미 승인된 DB 읽기 자격증명과 Storage 읽기 자격증명을 안전한 런타임에 제공한다. 권한 확대·키 생성·새로운 지속 접근 설정은 별도 승인 대상이다. 새 비밀 값을 채팅·셸 인수·Git에 붙이지 않는다.
4. libpq 환경은 `PGHOST=db.<project-ref>.supabase.co`, `PGDATABASE=postgres`, `PGUSER`, `PGPORT=5432`, `PGSSLMODE=verify-full`, 신뢰할 수 있는 `PGSSLROOTCERT`, 기존 승인된 `PGPASSFILE` 또는 런타임 비밀 주입을 사용한다. 직접 연결에 필요한 IPv6가 불가능하면 임의로 다른 프로젝트나 풀러로 우회하지 말고 승인된 연결 방법을 별도 검증한다.
5. `SUPABASE_SERVICE_ROLE_KEY`, `SNOTE_BACKUP_PASSPHRASE`를 승인된 런타임 비밀로 주입한다. 서비스 역할은 광범위한 권한이 있으므로 단기 프로세스 범위에만 사용한다. 도구는 이를 저장하거나 로그에 출력하지 않는다.
6. 기존 암호화 키의 안전한 복구 가능 여부를 확인한다. 백업 암호나 외부 복호화 키를 잃으면 데이터 파일이 있어도 복구하지 못할 수 있다.

실행 예시는 자리표시자이며 자격증명을 포함하지 않는다.

```sh
node scripts/snote-backup.mjs capture --project-ref PROJECT_REF --output /private/backup/snote-YYYYMMDDTHHMMSSZ.snbak
node scripts/snote-backup.mjs verify --input /private/backup/snote-YYYYMMDDTHHMMSSZ.snbak
```

`verified-encrypted-archive`는 암호화 패키지의 완전성 검사가 통과했다는 뜻이다. 별도 서버의 사본, 복구된 서비스, 예약 실행 성공을 의미하지 않는다. 외부로 복사할 때에는 승인된 목적지에만 보내고, 목적지에서 다시 내려받은 파일을 검증한다. 한 컴퓨터의 같은 디스크에만 있으면 재해 대비 사본으로 충분하지 않다.

## 복구 절차: 백업과 별개로 검증

1. 원본 장애와 복구할 시점을 확인하고 현재 운영을 덮어쓰지 않는 격리된 대상, 비용, 작업 범위의 승인을 받는다. 원래 백업은 변경하지 않는다.
2. 격리된 환경은 문자·메일·웹훅·정기 작업·`pg_cron`·`pg_net` 등 외부 통신이 먼저 차단되어 있어야 한다. Auth 세션 및 운영자 계정도 운영 서비스처럼 재활성화하지 않는다. 실고객 자료가 포함되므로 접근자를 제한한다.
3. 다음 명령은 **새 로컬 폴더로 평문을 추출할 뿐**, SQL 실행이나 운영 덮어쓰기를 하지 않는다.

```sh
node scripts/snote-backup.mjs extract --input /private/backup/snote-YYYYMMDDTHHMMSSZ.snbak --output /private/recovery/new-run
```

4. `inventory.json`, `roles.json`, `verified-manifest.json`을 기준으로 PostgreSQL 버전, 확장, 역할, 스키마 목록을 비교한다. `pg_restore --list database.dump`로 TOC를 검토한다. **raw 전체 pg_dump에는 Supabase 관리 스키마가 포함된다. 새 관리형 프로젝트에 무조건 pg_restore하면 역할·소유권·관리 스키마 충돌이 생길 수 있다.** 대상별 TOC 선택, 역할/권한, Auth/Storage 관리 스키마 복구 계획을 먼저 시험하고 승인한다. 이 도구는 자동 복구 명령을 제공하지 않는다.
5. 파일은 `objects/<hash>.blob`이고 원래 버킷/경로는 `inventory.json`에 있다. 모든 실제 파일을 승인된 복구 대상의 Storage API로 복원한다. **`storage.objects` 메타데이터만 복원해 파일이 되살아났다고 판단하지 않는다.** API 재업로드가 생성하는 객체 버전·소유자 정보와 DB 메타데이터를 대상 플랫폼에 맞게 조정해야 한다. 경로, 소유권, 버킷 비공개 설정, 파일 크기/해시 및 RLS를 다시 확인한다.
6. 전체 테이블 수·행 수·무결성, 차량/고객 연결, 계약서와 서명, 월정산과 차량 소득정산 금액, 휴지통·첨부파일 열기, 다른 상사 접근 차단을 확인한다. 외부 키가 필요한 암호문은 승인된 환경에서 실제 복호화도 확인한다. 브라우저 데이터가 과거 값을 다시 덮어쓰지 않도록 전환·재로그인·캐시 처리 계획도 준비한다.
7. 실제 소요시간, 복구 가능한 시점, 검증한 파일/행 수와 실패 항목을 기록한 후에만 별도 운영 전환 승인을 받는다. 추출된 평문은 민감자료로 계속 보호하며 승인된 보관/삭제 정책을 따른다.

## 보관 주기·비용: 제안이며 활성화되지 않음

- 초기 제안: 매일 1회, 최근 일간 7개 + 주간 4개 + 월간 12개. 별도 계정/장소에 검증된 사본을 유지한다. 실제 개인정보 보유기간·업무 요구·비용을 확인한 뒤 확정한다.
- 이 코드에는 스케줄러, 외부 업로드, 보관 만료 삭제가 없다. 마지막으로 검증된 정상 백업을 새 작업 실패 때문에 지우지 않는다.
- 매일 1회만으로는 성공한 마지막 백업 이후 최대 약 하루의 변경을 잃을 수 있으며, 실패하면 간격이 더 길어진다. 성공 알림뿐 아니라 실패·오래된 마지막 백업 경고도 운영 자동화에 필요하다.
- 보관 비용은 실제 DB·파일 크기, 사본 수, 암호화 오버헤드와 자료 증가량을 반영해 비공개 운영 기록에서 계산한다. 매일 전체 파일을 읽으면 월 30회 기준 파일 용량의 약 30배에 해당하는 다운로드가 발생할 수 있다. 실제 Storage/egress/보관 비용은 승인 전 현재 요금제로 확인한다.
- Supabase PITR는 별도 유료 옵션이다. 확인한 공식 문서의 7일/14일/28일 보관은 약 US$100/200/400 월 추가 요금이며 필요한 compute/요금제 비용이 별도일 수 있다. 결제·활성화하지 않았다. PITR도 실제 Storage 바이트 백업을 대신하지 않는다.

## 이번 검증 결과와 한계

- `node --test tests/backup-recovery.test.mjs`: 암호화 왕복, 오염/절단/재정렬/암호 오류, 파일 누락/크기/ETag/체크섬, 경로, 권한, 덮어쓰기 방지, 파이프라인 실패와 비밀 로그 차단을 검증한다. psql/pg_dump/pg_restore 파이프라인 테스트는 로컬 모의 실행 파일을 사용한다.
- `NODE_PATH=<PGlite 설치 경로> node tests/backup-recovery.sql.cjs`: 실제 PostgreSQL 엔진인 PGlite의 가상 상사 자료를 암호화한 뒤 새 DB로 복구해 전체 fixture 행, 정산·고객·서명·휴지통, 파일 바이트, 역할/RLS와 타 상사 접근 차단을 비교한다.
- PGlite 시험은 자체 `dumpDataDir/loadDataDir`를 사용한다. **운영 Supabase 또는 실제 `pg_dump/pg_restore`를 이용한 대상별 복구 시험이 아니다.** 실제 운영 접속 자격증명이나 파일 바이트는 사용하지 않았다.
- 실 운영 전체 백업 생성, 별도 장소 사본 검증, 실제 PostgreSQL 클라이언트 캡처, 관리형 Supabase 전체 복구, 키 복구, 앱 UI로 복구 자료 확인, 자동화/실패 통보는 아직 수행하지 않았다. 이 단계가 완료되기 전에는 “모든 운영 데이터의 복구 준비 완료”로 표시하지 않는다.
