# 계정 동시 로그인 제한

v2.114 수정본의 검증과 운영 DB 적용 확인을 완료했다. 웹 반영은 이 변경을 포함하는 GitHub 커밋의 Cloudflare Pages 배포 결과로 확인한다.

일반 로그인·운영자 로그인에서 다른 접속이 확인되면 `다른 곳에서 로그인 중입니다. 기존 접속을 해제하고 로그인하시겠습니까?`를 표시한다. **로그인**을 선택하면 기존 접속을 해제하고 새 로그인을 활성화하며 이전 화면에는 `다른 기기에서 로그인하여 로그아웃되었습니다.`를 표시한다. **취소**하면 기존 접속은 유지되고 새 로그인은 종료한다. 별도 설정은 없다.

## 세션 판정

- 실제 로그인 직후 `snote_session_claim()`을 **POST**한다. 다른 접속이 있으면 서버는 새 세션을 대기 상태로 두고 확인을 요청한다. 사용자가 동의한 뒤 확인한 세대 번호를 함께 보내고, 활성화 성공을 확인한 뒤에만 상사·차량 자료를 불러온다.
- 확인창을 열어 둔 사이 다른 로그인이 활성화되면 다시 확인한다. 취소·창 닫기·통신 오류만으로 기존 접속을 끊지 않는다. 확인을 기다리는 시간은 네트워크 응답 제한 시간에 포함하지 않는다.
- 확인 전 후보 로그인은 고유한 키를 가진 비영구 Auth 클라이언트에서 진행한다. 같은 브라우저의 다른 탭이 쓰는 인증 저장소와 BroadcastChannel은 바꾸지 않는다. 확인 후에만 활성 세대와 SID를 검증해 기존 인증 클라이언트로 승격한다.
- 각 인증 저장소는 세션과 세대에 고정한다. 이전 탭의 늦은 토큰 갱신·로그아웃·저장소 삭제가 새 세션을 지우거나 덮어쓰지 못한다. 승격 실패와 결과를 확인하지 못한 경우에도 새 후보를 활성 상태로 단정하지 않는다.
- 저장된 로그인 복원, 토큰 갱신, 화면 복귀와 재접속은 `snote_session_status()`만 호출한다. 기존 세션이 소유권을 다시 가져가지 않는다.
- 수익 잠금 해제 등 비밀번호 확인은 별도의 일시 Auth 클라이언트를 사용하고 활성 세션을 변경하지 않는다.
- 서버의 `auth.sessions.created_at`과 SID로 순서를 정한다. 먼저 시작한 로그인이 나중에 응답하더라도 더 새 로그인을 밀어내지 않는다.
- 활성 세션의 기록은 로그아웃·Auth 세션 삭제 후에도 순서 기준으로 남는다. 이전 토큰이 다시 살아나지 않는다.
- 배포 전에 유지되던 세션은 해당 계정의 첫 새 로그인 전까지 호환된다. 첫 전환에서도 다른 기존 접속을 확인하고 사용자에게 묻는다. 새 대기 세션은 업무 자료에 접근할 수 없다. 자동 복원으로 임의의 기존 기기를 승자로 선택하지 않는다.

## 화면과 서버

본인만 읽을 수 있는 `snote_session_signals`의 Realtime 알림은 재검사 신호다. 알림 내용만으로 로그아웃시키지 않는다. 화면에 보이는 동안 5초 간격의 보조 검사와 복귀·연결 복구 검사도 한다. 오프라인·검사 실패 시에는 화면을 잠그고 서버 작업을 중단하며, 유효한 확인 응답 후 다시 연다.

강제 종료는 저장 대기 작업을 서버로 밀어 넣지 않는다. 기존 계정별 로컬 캐시와 저장 복구용 범위·리비전·해시 표시만 보존한다. 이전 SID의 인증 저장소만 정리하고 새 기기의 세션이나 같은 브라우저에서 막 생성된 새 세션을 로그아웃시키지 않는다.

Data API의 pre-request 검사, authenticated 테이블의 추가 RLS 조건, Storage의 추가 RLS 조건이 기존 토큰의 접근을 막는다. 서비스 권한으로 실행하는 운영자 작업도 전달받은 실제 사용자·SID를 재검사한다. Cloudflare API는 인증된 요청을 처리하기 전에 동일한 상태 RPC를 검사한다. 공개 고객 직접입력·문자 인증 링크와 날씨·설정 상태 조회는 기존 인증 흐름을 유지한다.

기존 DB 작업과 새 로그인은 사용자별 advisory transaction lock으로 순서를 맞춘다. 검사 함수는 읽기 전용 트랜잭션에서도 동작하고, 잠금을 기다린 뒤 최신 스냅샷으로 상태를 다시 읽는다. HTTP 검사 결과는 캐시하지 않는다.

네트워크가 끊겼거나 기기가 절전 중이면 화면 갱신은 연결·복귀 시점에 이뤄진다. 서버 접근 제한은 화면 알림과 독립적이다. 이미 내려받은 자료·이미 발급된 서명 URL과 시작된 외부 전송을 되돌리지는 않는다.

## 확인 절차

1. 별도 브라우저 두 개에서 같은 시험 계정으로 A, B 순서로 로그인한다. B에서 확인창이 열리는 동안 A는 계속 사용할 수 있어야 한다.
2. B에서 취소하면 A는 유지되고 B에는 업무 자료가 표시되지 않는지 확인한다. B에서 다시 로그인하고 접속 해제를 확인하면 B는 정상 사용되고 A는 안내 후 로그인 화면으로 전환되는지 확인한다.
3. A의 옛 토큰으로 조회·저장·Storage·인증된 Cloudflare 요청을 보내 차단되는지 확인한다.
4. B에서 비밀번호 확인, 토큰 갱신, 새로고침을 해도 다른 세션을 새로 차지하지 않는지 확인한다.
5. 로그인 응답 역전, 통신 중단·복구, 늦은 저장 응답, 운영자 로그인도 확인한다.

안드로이드 앱은 별도 네이티브 로그인 코드에 같은 프로토콜을 적용한 업데이트가 필요하다. 웹 변경만으로 기존 APK의 화면 종료 코드를 바꿀 수는 없다. DB 접근 제한은 기존 APK의 옛 SID에도 적용된다.

## 운영 반영

2026-11-14에 사용자가 SQL Editor에서 단일 트랜잭션 파일을 실행했고, 운영 migration `20261109161432 / single_active_account_session`과 스키마의 적용을 읽기 전용으로 확인했다. 공개 RPC의 정확한 인자·기본값·권한, private 표 RLS·권한, 요청 훅, restrictive 정책, Realtime 등록 및 설치된 함수 본문이 검증 소스와 일치한다. SQL Editor가 이력의 개행을 CRLF로 바꿨지만 LF로 정규화하면 원본 SHA256 `003767344bb3a6e06245e02d38e4886c20f1abb3c1a46f8348c8e2b091be89de`와 정확히 일치한다.

DB 적용 파일은 `supabase/migrations/20261109161432_single_active_account_session.sql`이다. SQL Editor용 `/workspace/work/single-session-rollout/APPLY_v2_114_SINGLE_LOGIN.sql`은 같은 소스와 migration 이력 등록을 한 트랜잭션에 담았다. 이미 적용됐으므로 다시 실행하지 않는다. 운영 세션을 일괄 종료하지 않으며, 확인한 새 로그인부터 이전 접속을 전환한다.

연결 도구의 DB 쓰기 요청은 완료되지 않았고 대체 Management API 인증은 401이었다. 사용자가 승인한 임시 `모든 작업 허용` 재시도로도 해결되지 않아 기존 `Use my default`로 복구했고, 이후 사용자의 SQL Editor 실행으로 DB 적용을 마쳤다. 앱 권한이나 등록된 인증 키는 추가로 변경하지 않았다.
